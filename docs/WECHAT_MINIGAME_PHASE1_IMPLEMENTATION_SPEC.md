## 1. 项目目标

第一阶段不是制作完整游戏，也不是迁移现有 H5 的全部功能。

第一阶段只完成一个可验证的微信小游戏技术样板：

```text
小游戏启动
  -> 检查本地存档
  -> 无存档时进入创角页
  -> 选择性别和角色形象
  -> 输入或随机生成角色名
  -> 点击创建角色
  -> 写入本地存档
  -> 显示创建结果
  -> 关闭并重新启动后能够恢复同一角色
```

本阶段需要同时验证以下技术链：

1. Cocos Creator 项目可以构建为真正的微信小游戏。
2. 原版 960 × 640 UI 可以在微信 Canvas 环境正确渲染。
3. UI XML、ANI、PFDW HASH 图片之间的资源映射可以自动生成。
4. 原版按钮、立绘、字体和基础动画可以正确显示和交互。
5. 单机状态可以通过微信 Storage 保存、读取和版本迁移。
6. 工程结构能够支持第二阶段继续接入新手村和战斗，而不需要推翻重做。

## 2. 第一阶段完成定义（Definition of Done）

只有同时满足以下条件，第一阶段才算完成：

- 存在独立的 Cocos Creator 微信小游戏工程，不依赖现有 HTML 页面运行。
- 工程可以在 Cocos Creator 中打开且无资源导入错误。
- 工程能够成功构建微信小游戏产物。
- 构建产物可以被微信开发者工具导入和运行。
- 首次启动进入创角界面。
- 创角界面使用原版资源，不用临时色块或虚构图片代替。
- 可以切换男女角色以及 `CreateRoleConf` 中已确认的形象。
- 可以输入角色名，也可以触发随机取名。
- 创建按钮能够校验空名字并生成角色存档。
- 存档包含明确的 `saveVersion`，不能直接保存整个运行时对象。
- 重启小游戏后可以读取并显示之前创建的角色。
- 提供清除测试存档的开发入口，但该入口不得影响正常玩家界面。
- 960 × 640、常见宽屏和异形屏下均保持等比，不发生画面拉伸。
- 构建控制台不存在资源 404、未解析 ANI、重复资源 ID 或未找到 XML 控件错误。
- 主包只包含第一阶段需要的资源，不包含全部 10,213 张图片。
- 提供资源映射检查、存档检查和构建说明文档。
- 提供至少一组基准截图和微信开发者工具实际运行截图。

如果无法实际启动 Cocos Creator或微信开发者工具，AI 必须明确标记为“未验证”，不得把生成了文件等同于构建通过。

## 5. 数据和证据优先级

当不同来源存在冲突时，按以下优先级处理：

1. APK 原始文件、PFDW 目录、FDB/KFDB、ANI、UI XML。
2. 已验证的 PFDW 路径/section 映射和自动审计结果。
3. native 符号、字符串和反汇编中可重复确认的行为。
4. 当前 H5 的生成数据和运行行为。
5. 原游戏截图、录屏和玩家资料。
6. 仓库中的 GDD/TDD、推定设计稿和人工说明。

所有进入生成清单的数据必须具有下列证据状态之一：

| 状态 | 含义 | 第一阶段处理方式 |
|---|---|---|
| `confirmedLocal` | 从 APK/本地文件直接确认 | 可以使用 |
| `presentLocalNotWired` | 资源存在但尚未接线 | 可以在验证后接入 |
| `unresolvedLocal` | 概念存在但具体值未确认 | 不得猜测 |
| `notFoundLocal` | 本地没有找到 | 不得生成假资源 |
| `externalReviewed` | 外部资料经过人工审核 | 本阶段原则上不使用 |
| `redesigned` | 为可玩性重新设计 | 本阶段只允许非空名字等必要交互规则 |

AI 遇到来源冲突时应生成问题报告，不能静默选择一个值。

## 7. 技术架构

### 7.1 场景

第一阶段最多需要三个场景：

| 场景 | 职责 |
|---|---|
| `BootScene` | 初始化平台、读取存档、决定跳转 |
| `CreateRoleScene` | 原版创角页面和交互 |
| `RoleCreatedScene` | 显示已创建角色，用于验证持久化 |

`RoleCreatedScene` 是第一阶段技术验收页，不代表最终游戏页面。第二阶段可以将它替换为 `RookieFieldScene`。

### 7.2 运行时模块

只实现具有明确职责的最小模块：

| 模块 | 职责 |
|---|---|
| `AppBootstrap` | 初始化并切换第一个场景 |
| `RoleCreationService` | 处理创角输入并生成角色状态 |
| `RoleSave` | 定义可持久化角色数据结构 |
| `SaveRepository` | 保存、读取、删除和迁移存档 |
| `PlatformStorage` | 隔离微信 Storage 与浏览器预览存储 |
| `AssetRegistry` | 根据稳定资源 ID 查询生成资源 |
| `CreateRoleView` | 只负责显示和输入 |
| `CreateRoleController` | 连接视图与领域状态 |

不要引入 ECS、依赖注入框架、Redux、复杂事件总线或通用 UI 框架。本阶段没有足够复杂度支撑这些抽象。

### 7.3 存储适配

生产目标使用微信 Storage；Cocos 浏览器预览可以使用 Web Storage。两者通过一个最小接口隔离：

```text
load(): RoleSave | null
save(data: RoleSave): void
remove(): void
```

不得在业务代码各处直接调用 `wx.setStorageSync` 或 `localStorage`。

## 8. 资源注册表规格

### 8.1 目标

将旧客户端的多层资源引用统一为稳定注册表：

```text
XML 控件引用
  -> ANI 文件与 section
  -> ANI Frame 逻辑路径
  -> PFDW Hash
  -> res_HASH.png
  -> Cocos 生成资源路径
```

### 8.2 建议字段

每个资源记录至少包含：

```text
id                  稳定逻辑 ID
type                image / animation / font / audio
logicalPath         data/... 原始逻辑路径
aniFile             ANI 文件名，可空
aniSection          ANI section，可空
hash                8 位十六进制 PFDW Hash
sourcePath          原始 HASH 文件路径
generatedPath       Cocos 工程内生成路径
width               图片宽度
height              图片高度
drawMode            simple / sliced / tiled / center-crop
usage               create-role/background/button/portrait 等
evidenceStatus      证据状态
evidenceSource      来源文件和定位信息
```

动画记录还应包含：

```text
frames[]
frameDuration
loop
offsetX
offsetY
scale
```

如果 ANI 没有明确给出帧时长，使用能够确认的原客户端默认值，并记录来源；不得引用未经验证的 GDD 数值。

### 8.3 第一阶段依赖闭包

资源脚本应从以下入口开始递归收集：

```text
CreateRole.xml
CreateRoleConf.csv
CreateRoleInfo.csv
CreateRole 页面引用的 ANI section
CreateRole 页面引用的字体和按钮音效
```

输出只能包含创角技术样板实际使用的依赖。

必须生成统计：

- XML 控件数量。
- ANI section 数量。
- 唯一 PNG 数量。
- 字体和音频数量。
- 未解析引用数量。
- 重复 ID 数量。
- HASH 文件缺失数量。
- 最终资源总字节数。

未解析引用必须为 0，或者在验收报告中逐项说明为何不影响可见结果。

## 9. UI 转换和渲染规则

### 9.1 坐标系统

原 UI 使用 960 × 640 设计坐标。转换器必须建立统一的顶点和锚点规则，禁止每个控件各自写坐标补丁。

推荐做法：

- 页面根节点代表 960 × 640 逻辑画布。
- 统一采用左上角作为旧 XML 坐标原点。
- 在单一转换函数中处理 XML 坐标到 Cocos UI 坐标的转换。
- 子控件保持原 XML 层级和相对坐标。
- Z 顺序服从 XML 元素顺序和明确层级字段。

转换公式和锚点约定必须写入运行文档。

### 9.2 控件映射

第一阶段只实现 `CreateRole.xml` 实际使用的控件类型：

| 旧控件 | Cocos 节点 |
|---|---|
| 页面/容器 | Node + UITransform |
| 静态图片 | Sprite |
| 动画图片 | Sprite + Animation |
| 按钮 | Button + Sprite 状态 |
| 文本 | Label 或 RichText |
| 输入框 | EditBox |
| 可见状态 | Node.active |

遇到未使用控件类型时不得提前构建通用系统。

### 9.3 背景模式

旧资源可能包含 `name:mode` 形式的背景引用。已知 `dialog_rimbg8:2` 在研究原型中采用 1200 × 768 原图居中裁切到 960 × 640。

第一阶段只实现创角页实际出现的绘制模式，并为每种模式保存显式枚举：

- `simple`
- `sliced`
- `tiled`
- `center-crop`

不得通过图片文件名猜测绘制模式。

### 9.4 屏幕适配

- 游戏固定横屏。
- 逻辑内容保持 960:640 比例。
- UI 不能非等比拉伸。
- 宽屏多出的区域使用背景延展或留边。
- 关键按钮、输入框和角色立绘必须处于安全区。
- 安全区只影响外层画布适配，不应破坏 XML 内部坐标。

至少验证：

- 960 × 640。
- 1280 × 720。
- 2436 × 1125 等宽屏比例。
- 微信开发者工具提供的一个 iOS 和一个 Android 模拟设备。

## 10. 创角功能规格

### 10.1 数据来源

- 角色形象：`CreateRoleConf.csv`。
- 随机姓和名：`CreateRoleInfo.csv` 或当前已确认的 runtime seed。
- 视觉布局：`CreateRole.xml`。
- 按钮和立绘：UI XML + ANI section + HASH PNG。
- 字体：原始 `font.ttf`，并配置系统字体回退。

### 10.2 初始状态

优先采用 `CreateRoleConf` 和当前 H5 runtime seed 中已经确认的默认性别、默认形象和默认名字。

如果默认值在不同来源中冲突，使用证据优先级处理并记录。

### 10.3 交互

必须支持：

- 切换男性/女性。
- 在当前性别对应的形象中前后切换。
- 显示当前角色形象。
- 输入角色名。
- 生成随机角色名。
- 点击创建。
- 空名字时阻止创建并给出简短提示。

不得自行增加职业选择、属性分配、付费形象或稀有度。

如果原数据没有名字长度限制，本阶段只做去除首尾空白和非空校验，不猜测原版长度规则。

### 10.4 创建结果

创建成功后生成稳定的本地角色 ID，并保存角色信息。角色 ID 可以是本地生成的 UUID，不宣称为原版规则，证据状态记为 `redesigned`。

保存成功后进入 `RoleCreatedScene`，显示：

- 角色名。
- 性别。
- 形象。
- 本地角色 ID 的开发调试信息可以进入调试面板，不应作为主视觉大段显示。

## 11. 存档规格

存档键使用项目专属名称，例如：

```text
daming_minigame_single_save
```

建议最小结构：

```text
saveVersion
roleId
roleName
sex
appearanceId
professionId
currentScene
guideStep
createdAt
updatedAt
```

要求：

- `saveVersion` 初始值为 1。
- 所有字段必须有清晰类型。
- 读取时进行基本结构验证。
- 损坏存档不能导致白屏，应进入可恢复状态并记录错误。
- 未知未来版本的存档不得静默覆盖。
- 删除存档只允许通过开发调试入口或明确确认操作。
- 本阶段不需要加密，不要编写伪安全方案。
- 本阶段不需要多存档槽。

`professionId` 如果创角阶段尚未确定，应使用明确的 `null`，不得随便分配职业。

- 检查工作区现有修改，不覆盖用户文件。
- 定位 Cocos Creator 安装路径和版本。
- 定位微信开发者工具安装路径和版本。
- 确认三个 PFDW/ANI 映射文件是否可读。
- 确认 `CreateRole.xml`、CSV、ANI、字体和 HASH PNG 是否存在。
- 输出 `minigame-phase1-evidence-report.md`。

验收：

- 所有必要输入存在并记录绝对或仓库相对路径。
- 缺失项被明确列出。
- 未对原始资源做修改。

### P1-01：创建 Cocos 工程骨架

任务：

- 使用实际安装的 Cocos Creator 3.x 创建项目。
- 配置横屏和 960 × 640 设计分辨率。
- 创建 `BootScene`、`CreateRoleScene`、`RoleCreatedScene`。
- 配置微信小游戏构建目标。
- 完成空场景构建验证。

验收：

- Cocos 项目可以打开。
- 空项目构建微信小游戏成功。
- 微信开发者工具能够启动构建结果。

### P1-02：建立创角资源注册表

任务：

- 读取 UI XML、ANI section 映射、路径映射和 PFDW 索引。
- 计算创角页面资源依赖闭包。
- 将所需 HASH PNG 复制到生成目录。
- 生成 `asset-registry.json`。
- 生成资源审计报告。

验收：

- 重复资源 ID 为 0。
- 缺失 HASH 文件为 0。
- ANI frame 未解析数量为 0。
- 没有复制无关的 10,000 多张图片。

### P1-03：转换创角 UI 描述

任务：

- 解析 `CreateRole.xml`。
- 保留控件层级、坐标、尺寸、可见性、文本和资源引用。
- 输出 `create-role-ui.json`，或者生成结构清晰的 Cocos Prefab。
- 将坐标转换集中到单一模块。

验收：

- XML 中需要显示的控件全部有对应节点。
- 没有散落的硬编码坐标修正。
- 节点层级与原 XML 对应。

### P1-04：转换创角动画和按钮状态

任务：

- 将创角所需 ANI section 转换为 AnimationClip 或明确的帧描述。
- 建立按钮 normal/pressed/disabled 映射。
- 建立角色形象切换映射。

验收：

- 每个帧引用都能定位到资源注册表。
- 按钮按下不会改变布局尺寸。
- 动画循环和非循环行为有明确数据来源。

### P1-05：实现创角交互

任务：

- 连接性别切换。
- 连接形象切换。
- 连接输入框。
- 连接随机取名。
- 连接创建按钮和空名字提示。
- 创建成功后进入结果场景。

验收：

- 所有操作在鼠标和微信触控模拟下都有效。
- 连续快速点击不会导致数组越界或多个场景重复加载。
- 最长可见名字不会溢出输入框和结果界面。

### P1-06：实现单机存档

任务：

- 定义 `RoleSave`。
- 实现微信 Storage 适配。
- 实现浏览器预览 Storage 适配。
- 实现读取、保存、删除和版本检查。
- `BootScene` 根据存档决定进入创角或结果场景。

验收：

- 首次启动无存档进入创角。
- 创建后立即产生有效存档。
- 关闭并重启后恢复相同角色。
- 删除测试存档后重新进入创角。
- 损坏测试存档不会导致启动白屏。

### P1-07：视觉和设备适配

任务：

- 对照当前 H5 创角截图或生成截图调整可验证的渲染差异。
- 验证原字体和字体回退。
- 验证宽屏、安全区、横屏和触摸区域。
- 记录无法确认的旧引擎绘制差异。

验收：

- 960 × 640 基准画面中无明显错层、拉伸或资源错挂。
- 宽屏中核心画面保持比例。
- 文本、按钮和立绘不重叠。
- 点击区域与视觉按钮一致。

### P1-08：构建、测试和交付

任务：

- 运行自动资源检查。
- 运行存档单元测试或等价自动检查。
- 执行 Cocos 微信小游戏构建。
- 在微信开发者工具中运行。
- 截取首次创角、切换形象、创建成功、重启恢复四类截图。
- 完成运行手册和验收报告。

验收：

- 所有 Definition of Done 项目逐条标记结果。
- 未执行项说明原因，不能写成通过。
- 交付结果能够由另一名开发者按照 README 重复运行。

## 13. 自动检查要求

至少提供以下自动检查：

### 13.1 资源注册表检查

- `id` 唯一。
- HASH 格式正确。
- 每个 `sourcePath` 存在。
- 每个动画帧引用存在。
- 每个生成资源路径存在。
- 不允许路径逃出指定源目录和生成目录。

### 13.2 UI 描述检查

- 页面根尺寸为 960 × 640。
- 控件 ID 在页面内唯一。
- 所有可见图片资源可解析。
- 控件宽高不是意外的负数或零。
- 未支持控件类型有明确报告。

### 13.3 存档检查

- 空存档。
- 正常 v1 存档。
- JSON/结构损坏存档。
- 缺少必要字段存档。
- 高于当前 `saveVersion` 的未来存档。

### 13.4 构建检查

- Cocos 工程配置存在。
- 微信小游戏构建产物存在。
- 构建日志中没有 error。
- 第一阶段资源清单中不存在全量图片目录误打包。

## 14. 视觉基准

视觉判断顺序：

1. 原始 XML 坐标和尺寸。
2. ANI section 对应的真实帧。
3. 当前 H5 的 `CreateRole` 页面。
4. 仓库截图和本地渲染截图。

截图对比至少检查：

- 背景裁切。
- 角色立绘位置和尺寸。
- 男女切换状态。
- 上一形象/下一形象按钮。
- 名字输入框。
- 随机取名按钮。
- 创建按钮。
- 字体、颜色和描边。
- 控件层级和遮挡。

允许第一阶段存在轻微字体栅格化差异，但不允许资源错挂、严重错位、拉伸、按钮热区偏移或文字溢出。

## 15. 性能和包体原则

第一阶段不设未经测量的绝对性能数字，但必须遵守：

- 不导入全量 HASH 图片。
- 不在启动时扫描 10,213 个文件。
- 资源映射在构建时生成，运行时只读取小型注册表。
- 创角场景离开后能够释放不再使用的临时资源。
- 不生成一个包含所有游戏资源的巨型图集。
- 不因按钮状态切换重复加载同一张图片。
- 不在每帧解析 XML、ANI 或 JSON。
- 记录微信开发者工具中的首屏加载时间、内存和资源数量作为后续基线。

是否制作图集应以第一阶段实际资源数量和透明边缘情况决定，不要为了“优化”提前破坏原始切图坐标。

## 16. 禁止事项

编码 AI 不得执行以下做法：

- 将现有 H5 放进 WebView 并称为微信小游戏完成。
- 在小游戏中依赖 `document`、DOM 或 CSS 布局。
- 修改、重命名或覆盖原始逆向资产。
- 一次性把 10,213 张 PNG 拖入 Cocos。
- 人工猜测 HASH 图片对应的逻辑资源。
- 忽略现有 `libdata-ani-*` 映射重新写未经验证的 HASH 算法。
- 把 GDD/TDD 中的推测值当作 APK 原始证据。
- 为了消除报错而用透明图、色块或错误图片替代缺失资源。
- 把所有逻辑写进一个场景脚本。
- 在业务代码中到处直接调用微信 API。
- 添加服务器、登录、支付、排行榜、社交或战斗系统。
- 顺手重构现有 H5。
- 在没有实际运行时声称微信开发者工具验证通过。

## 17. AI 执行过程要求

AI 应按以下方式工作：

1. 先读取目标仓库 README、当前状态和本规格书。
2. 检查 `AGENTS.md` 或其他仓库规则。
3. 检查工作区已有改动并保留用户修改。
4. 形成不超过 8 项的实施计划，每项包含验收方式。
5. 先完成 P1-00，再开始创建工程。
6. 每完成一项就运行对应检查，不要最后一次性验证。
7. 只做与第一阶段直接相关的修改。
8. 优先复用现有解析成果和工具，不复制粘贴大段生成数据。
9. 对生成文件保留明确的生成来源，能重复构建。
10. 最后执行完整构建和微信开发者工具验证。

AI 只有在以下情况才应暂停提问：

- 无法找到三个关键映射文件，也无法访问本机研究工程。
- 无法找到实际 HASH PNG 源文件。
- 用户要求的 Cocos 主版本与已安装版本冲突。
- 需要安装大型软件但没有授权或安装条件。
- 微信开发者工具要求用户本人扫码登录才能继续。

扫码登录属于正常人工边界。AI 应先完成所有无需登录的工作，再明确告诉用户需要在哪一步扫码。
