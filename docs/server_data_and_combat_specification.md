## 一、 系统架构定位与权威分工总览

在网龙 C3 引擎原版设计及现代化重构体系中，**服务端是所有核心数值、状态变化及战斗推演的唯一权威仲裁者**。

```text
+-----------------------------------------------------------------------------------------+
|                                    系统权威分工架构图                                     |
+-----------------------------------------------------------------------------------------+
|                                                                                         |
|      【前端 / 客户端 (Web / Canvas / libEnvRelay.so)】                                  |
|         │                                                                               |
|         ├─ 1. 提交战斗请求 (如请求打副本: action=city_dungeon_pk, stage=1)              |
|         │                                                                               |
|         │                        ▼ (HTTP / WebSocket)                                   |
|         │                                                                               |
|      【后端权威推演层 (Node.js + Express + CombatSimulator)】                           |
|         │                                                                               |
|         ├─ 2. 读取角色十维属性、当前装备属性与已装配的 3 个出战技能 (`used_skills`)     |
|         ├─ 3. 读取当前关卡波次配置及对应的怪物模板属性 (`dungeon_monsters`)              |
|         ├─ 4. 在微秒级内完整执行整场战斗演算：                                          |
|         │    - 速度排序决定先后手轮次                                                   |
|         │    - 九宫格前排优先索敌                                                       |
|         │    - 技能气力判定 (MP充足放绝招，不足则普攻)                                  |
|         │    - 命中率、暴击率、格挡破防伤害计算                                         |
|         │    - 逐回合记录 Action (攻击者、受击者、技能ID、扣血量、暴击/闪避标识)        |
|         ├─ 5. 判定最终胜负 (`is_win`)，在数据库中原子结算角色经验、银两、战功、装备掉落  |
|         ├─ 6. 打包生成完整回合战报 JSON (`rounds`) 回传给客户端                         |
|         │                                                                               |
|         │                        ▼ (下发战报 JSON)                                      |
|         │                                                                               |
|      【前端展示与播放层 (CBattle 播放器)】                                               |
|         │                                                                               |
|         ├─ 7. 客户端接收战报，按 `rounds` 逐帧播放冲锋动作、打击特效 SWF 与受击音效 OGG |
|         └─ 8. 若玩家勾选或点击“跳过战斗”，直接读取 `is_win` 弹出结算面板               |
|                                                                                         |
+-----------------------------------------------------------------------------------------+
```

### 权威归属的逆向铁证：
1. **`CBattle::ProcessBattleInfo`（物理地址 `0x00535B0C`）**：
   客户端底层动态库 `libEnvRelay.so` 中，处理战斗的函数入口为 `CBattle::ProcessBattleInfo`。反汇编表明，该函数纯粹作为 JSON 解析器，读取服务端下发的 `rounds` 节点、`attacker` 阵位、`target` 阵位、`damage` 扣血量与 `is_cri` 标志，随后调用动画系统。**客户端本地完全没有战斗伤害公式与判定逻辑**。
2. **VIP 跳过战斗 `see_result_button_state`**：
   客户端允许玩家在战斗刚开局或任意时刻点击“跳过战斗”直接展示胜利或失败画面。这从工程机制上直接证明：**胜负结果在服务端接收到挑战请求的第 1 毫秒就已经计算完毕并持久化，战斗动画只是事后回放**。

## 二、 数据权责归属全景清单 (三维权责矩阵)

在游戏的全部数据资产中，必须严格划清边界：哪些是客户端本地只读的，哪些由服务端下发，哪些需要由我们自己编写实现。

### 2.1 第一类：客户端原生只读静态表（本地加载，无需服务端传输）
位于 `extracted_full_resources/server_data/tables_csv/`，属于客户端内置资产：
1. `CreateRoleConf.csv`：创角外观模型映射（男女各 20 套模型）。
2. `CreateRoleInfo.csv`：随机起名百家姓库（292 姓氏 + 348 名字）。
3. `BattlePos.csv`：战斗九宫格站位像素坐标（攻方 1~9 号位、守方 1~9 号位像素偏移）。
4. `BattleSetting.csv`：战斗表现时序参数（冲锋 800ms、击退 400ms、受击震屏 60ms）。
5. `SkillAction.csv` / `Sound.csv`：技能动作、光效 SWF 与音效 OGG 物理文件映射表。
6. `MapSetting.csv` / `MapInsideGate.csv`：主城城门热区与大地图视口边界。

### 2.2 第二类：服务端权威下发动态协议（客户端无静态大表）
客户端本地不存储任何静态成长数值大表，全部在玩家交互时由服务端下发 JSON：
1. **角色核心状态**：角色等级、经验、元宝、银两、战功、VIP、当前气血、当前十维属性。
2. **装备属性数据**：装备唯一实例 ID、强化等级、基础加成（`howmuch`）、强化成长步进（`up_base`）、武种限制（`wuzhong_limit`）、属性类型（`shuxing_att`/`shuxing_def`）、特殊词条与价格。
3. **技能元数据与出战配置**：技能名称、当前等级、伤害基数（`howmuch`）、每级成长（`up_base`）、气力消耗（`use_cost`）、当前已装配出战的 3 个技能列表（`used_skills`）。
4. **关卡波次与掉落结果**：通关评星、历史最优回合、本次通关获得的经验/银两/战功及掉落装备。
5. **战斗全回合战报**：包含全局胜负、总回合数、每个小回合的行动者、目标、招式、伤害、暴击/闪避状态。

### 2.3 第三类：必须自主编写实现的核心业务与推演模块
原版服务端代码未开源，因此以下核心逻辑与数据必须由我们自主编写：
1. **服务端战斗推演模拟器 (`CombatSimulator.js`)**：
   - 速度降序先手队列算法；
   - 九宫格前排索敌寻路逻辑；
   - 气力积累与主动绝技/普攻切换状态机；
   - 命中、闪避、暴击、破防伤害公式推演；
   - 完整 `rounds` 战报数据流组装器。
2. **关卡怪物十维同构属性表 (`dungeon_monsters.json` / SQLite)**：
   - 包含广州新手通道到各大州府副本的怪物全属性与出战技能搭配。
3. **关卡波次配置表 (`dungeon_stages.json` / SQLite)**：
   - 关卡小节、怪物站位阵型、通关奖励与物品掉落概率池。
4. **装备强化洗练逻辑与模板表 (`equip_templates.json` / SQLite)**：
   - 装备数值底表、强化成功率、属性成长计算器。
5. **SQLite 轻量级持久化与协议网关**：
   - 用户会话、角色数据增删改查、事务操作与 CMsg 协议 JSON 封装。

## 三、 角色门派转职体系详解

### 3.1 初始唯一起点：混混 (ID: 1000)
- **初始定位**：所有玩家在创建角色进入大明世界时，唯一门派均为【混混】。
- **背景设定**：身处市井、手持竹竿晾衣杆、善用下三滥手段（吐口水、撒沙土、抄板砖），兼具顽强的生存能力（自带被动【厚脸皮】）。

### 3.2 20 级转职门槛与主线触发点
- **硬性等级门槛**：**20 级**。
  - 铁证：官方语言字典 `strres.ini` 编号 361309 明确记录系统提示：“升到20级即可转职”。
- **主线推进契机**：
  - 发生在新手主线第 38 步（玩家初入福州城 City 5）；
  - 由新手引导 NPC【小翠】触发剧情对话，激活客户端动作指令 `go2careercenter`，引导玩家前往【职业会所】。

### 3.3 三大进阶门派特性差异
达到 20 级后，玩家可在职业会所选择三大进阶门派之一：

```text
                           ┌──> 攻将 (ID: 1001) [物理爆发、破甲、暴击重劈]
                           │
混混 (ID: 1000) ──[20级]───┼──> 防将 (ID: 1002) [极限生存、嘲讽反伤、金钟罩]
                           │
                           └──> 阉派 (ID: 1003) [法术策攻、吸血吸星、千针封穴]
```

1. **攻将 (1001)**：
   - 定位：单体极致物理爆发与群体横扫；
   - 核心特点：攻击成长极高，技能附带破防与流血，克制防御薄弱的脆皮目标。
2. **防将 (1002)**：
   - 定位：团队肉盾、群体嘲讽与反弹伤害；
   - 核心特点：生命与物防成长极高，拥有【嘿孙子】强制嘲讽与【龟壳反弹】伤害反射，是前排防守的核心中坚。
3. **阉派 (1003)**：
   - 定位：法术输出、吸血续航与诡异减益；
   - 核心特点：法术攻击（策攻）与暴击见长，招牌技能【吸星大法】与【千针万雀】可在造成高额法术伤害的同时按百分比汲取生命。

### 3.4 转职惩罚与资产继承契约
通过对 `libEnvRelay.so` 中 `CCareerCenter` 模块的逆向分析，转职遵循严格的契约逻辑：
1. **装备限制**：转职前**必须卸下当前穿戴的武器**（各门派专属武器类型互斥：攻将用斧、防将用盾/锤、阉派用针/软剑）；
2. **技能重置**：除通用基础技能【暗界波】保留外，原混混专属的主动战斗技能重置回 1 级；
3. **战功 100% 退还**：玩家此前在混混技能上消耗的全部战功，系统**全额无损退还**至角色战功储备（`merit`），供玩家立即投入到新职业技能的学习与升级中；
4. **被动【厚脸皮】永久继承**：混混阶段修炼的被动强身技【厚脸皮】所提供的物理防御加成**永久保留，终身受益**。

## 四、 技能双轨制与出战限制体系

### 4.1 技能双轨制设计原则
《大明浮生记》客户端 `CSkill` 模块严格实行“双轨制”技能体系：

```text
+-----------------------------------------------------------------------------------------+
|                                    技能双轨制结构模型                                     |
+-----------------------------------------------------------------------------------------+
|                                                                                         |
|  【主动战斗技能池 (listFightSkill)】             【被动强身技能池 (listStrengSkill)】    |
|  - 拥有主动出招动画与光效 SWF                   - 无主动出招动作，属于被动心法           |
|  - 消耗 MP 气力值释放                           - 无需消耗 MP，永久生效                  |
|  - 包含攻击伤害、嘲讽、流血、封穴               - 直接永久提升角色十维属性               |
|  - 核心限制：每人严格限选 3 个装配出战          - 核心规则：全员全学，永不占出战槽位     |
|                                                                                         |
+-----------------------------------------------------------------------------------------+
```

### 4.2 战斗限选 3 个出战技能机制
- **逆向代码依据**：
  在 `libEnvRelay.so` 的 `CPnlSelSkillInfo::OnChkSkill`（地址 `0x00256154`）中，客户端维护勾选计数器。当选中的技能数达到 3 个时，其余技能的 CheckBox 强制置灰禁用。
- **协议下发字段**：
  在角色信息回包 `CRoleInfo` 中，维护字段 `used_skills`（整型数组，长度上限为 3，例如 `[1001, 1002, 1003]`）。
- **推演释放规则**：
  战斗中，角色每次获得出手权时：
  1. 依次扫描 `used_skills` 中的 3 个出战技能；
  2. 优先选取满足冷却时间且当前 MP 足够扣除（$\text{MP} \ge \text{use\_cost}$）的高阶技能释放；
  3. 若 3 个技能均因气力不足或 CD 无法释放，则角色降级执行基础物理普通攻击。

### 4.3 战功升级公式与全额返还洗点
- **战功升级消耗公式**：
  $$\text{消耗战功} = \text{upd\_cost\_base} \times (1 + \text{当前等级} \times \text{upd\_cost\_time})$$
- **属性成长公式**：
  $$\text{技能当前附加伤害/属性} = \text{howmuch} + (\text{技能等级} - 1) \times \text{up\_base}$$
- **洗战功机制 (`SendWashSkill`)**：
  支持随时重置技能。重置后技能归回到 1 级，历史上投入的战功 100% 全额返还给角色，杜绝加错点废号的惩罚。

## 五、 战斗推演模拟器 (CombatSimulator) 运算机制

### 5.1 权威推演 vs 前端播放职责边界
- **推演端 (Server Node.js)**：在内存中完成全局数值运算，负责输出最终结果与完整过程动作报文；
- **展示端 (Client Canvas / Web)**：严格消费报文，逐帧映射 `SkillAction.csv` 驱动动画切片、骨骼偏移与音效播放。

### 5.2 回合推演时序与九宫格站位
九宫格站位坐标直接基于客户端 `BattlePos.csv`：
- **攻方阵位**：`att1` 到 `att9`（1~3 前排，4~6 中排，7~9 后排）；
- **守方阵位**：`def1` 到 `def9`（1~3 前排，4~6 中排，7~9 后排）。

```text
       【攻方阵型】                      【守方阵型】
   [att7] [att4] [att1]              [def1] [def4] [def7]
   [att8] [att5] [att2]   VS 对决    [def2] [def5] [def8]
   [att9] [att6] [att3]              [def3] [def6] [def9]
     后排   中排   前排                前排   中排   后排
```

### 5.3 先手判定与前排优先索敌规则
1. **先手出手顺序**：
   每回合开始前，推演器汇集攻守双方所有存活单位，按各单位的十维属性 `speed` 进行降序排列。速度最高者获得第一出手权，以此类推。
2. **前排优先索敌原则**：
   - 目标阵营若前排（1~3 号位）存在存活角色，单体招式必须优先锁定对应对位的前排目标；
   - 若对位无目标，则向相邻的前排阵位顺延；
   - 只有前排目标全部被消灭后，攻击方才允许攻击中排与后排目标。

### 5.4 伤害、暴击、闪避与破防公式
推演器严格执行以下数值逻辑：
1. **命中判定**：
   $$\text{命中率} = \min\left(0.98, \max\left(0.10, \frac{\text{攻方命中} - \text{守方闪避} + 90}{100}\right)\right)$$
   若随机数大于命中率，则判定为【未命中/闪避】（`is_dodge = 1`），伤害为 0。
2. **暴击判定**：
   $$\text{暴击率} = \min\left(0.75, \max\left(0.05, \frac{\text{攻方暴击}}{100}\right)\right)$$
   若触发暴击，暴击倍率为 $1.5\times$。
3. **伤害计算（防御减免模型）**：
   $$\text{有效攻击} = \text{攻方物攻} + \text{技能附加伤害}$$
   $$\text{基础受击伤害} = \max\left(1, \text{有效攻击} \times \frac{100}{100 + \text{守方防御}}\right)$$
   $$\text{最终扣血量} = \lfloor \text{基础受击伤害} \times (\text{是否暴击} ? 1.5 : 1.0) \rfloor$$

### 5.5 战报协议结构契约 (rounds 结构)
下发给前端的 JSON 战报格式必须与 `CBattle::ProcessBattleInfo` 严格对齐：

```json
{
  "is_win": 1,
  "total_rounds": 3,
  "rounds": [
    {
      "round_num": 1,
      "attacker": { "is_player": 1, "pos": 2, "name": "主角" },
      "skill": { "id": 1001, "name": "暗界波", "is_magic": 0 },
      "target": { "is_player": 0, "pos": 2, "name": "市井流氓" },
      "damage": 52,
      "is_cri": 1,
      "is_dodge": 0,

    }
  ],
  "settlement": {
    "exp": 40,
```

## 七、 装备属性体系与强化成长模型

### 7.1 装备元数据与 6+1 槽位定义
角色装备栏拥有 6 大核心部位与 1 个恶搞扩展槽位：
1. `weapon`（主手武器）：增加物理攻击或法术攻击；
2. `armor`（胸部衣服）：增加物理防御与法术防御；
3. `waist`（腰部束带）：增加最大生命值上限；
4. `foot`（足部战靴）：增加出手速度与闪避率；
5. `ring`（首饰戒指）：增加物理/法术攻击与暴击；
6. `necklace`（颈部项链）：增加生命与内力上限；
7. `face`（恶搞脸皮）：增加专属生存减免与恶搞嘲讽抵抗。

### 7.2 服务端动态下发协议字段
由 `CItemMgr::ParseAct` 逆向证实，服务端下发装备遵循标准 JSON 字典：
- `item_id`：装备配置模板 ID；
- `item_name`：装备中文名（如“一星晾衣杆”）；
- `slot_type`：部位槽位代码；
- `howmuch`：初始基础属性值；
- `up_base`：每强化 1 级增加的基础属性成长步进；
- `wuzhong_limit`：职业限制（0 全通用，1000 混混，1001 攻将，1002 防将，1003 阉派）；
- `shuxing_att` / `shuxing_def`：物理/法术属性增益值；
- `weapon_effect`：装备描述与恶搞背景故事；
- `price`：典当出售价格。

### 7.3 强化属性公式与铁匠打造机制
1. **强化属性计算公式**：
   $$\text{当前实时属性} = \text{howmuch} + \text{强化等级} \times \text{up\_base}$$
2. **铁匠铺打造机制**：
   - 消耗银两与对应材料（钻石、水晶、玛瑙）打造高星级装备；
   - 强化等级随等级提升递增，受角色当前等级上限钳制（最高不可超过角色等级）。

## 八、 前期 SQLite 单文件运行时数据库架构

### 8.1 选型依据与架构优势
1. **完全自包含，零运维门槛**：
   前期开发直接采用 `better-sqlite3` 生成本地单文件 `server/daming.db`。无需搭建复杂的 MySQL 服务、无须配置账号密码与端口，克隆代码后直接启动即可运行；
2. **超高并发与微秒级读写**：
   `better-sqlite3` 是 Node.js 生态内最强悍的同步 C++ 绑定驱动。开启 WAL（Write-Ahead Logging）模式后，读写互不阻塞，单秒事务处理可达上万次，延迟低于 0.1ms；
3. **严格的 ACID 事务原子性**：
   买卖装备、升级技能扣战功、通关结算发奖等复合操作由原生数据库事务保障，彻底杜绝内存对象 mock 时容易发生的并发脏读与丢数据问题；
4. **与未来 MySQL/PostgreSQL 100% 语法对齐**：
   所有 DDL 与 SQL 语句遵循标准 ANSI-SQL，表结构与关系清晰明确，后续支持联机上云时可一键迁移。

### 8.2 核心 DDL 模式与表间关系

```text

                                        │ 1
                         ┌──────────────┼──────────────┐
                         │ 1:N          │ 1:N          │ 1:N
                         ▼              ▼              ▼

              | role_id (FK)       | | role_id (FK)       | | dungeon_id (PK)    |
              | equip_tpl_id (FK)  | | skill_id (FK)      | | pass_times         |
```

### 8.3 基础数据加载与平滑演进路线
1. **数据源分层**：
   - 基础静态配置：保存在 `server/data/baseline/` 下的 JSON 文件中（`equip_templates.json`, `skill_templates.json`, `monster_templates.json`, `dungeon_stages.json`）；

2. **平滑演进**：
   - 第一阶段（Phase 1）：SQLite 单文件驱动单机/局域网闭环；
   - 第二阶段（Phase 2）：接入武将招募、经脉洗髓、城池漫游；
   - 第三阶段（Phase 3）：无缝平移至 MySQL/PostgreSQL 支持公网多人联机。
